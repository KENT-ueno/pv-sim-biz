# データセンターMCPツールの実機検証手順（Codex / Claude Code）

設計書 `design_spec.md` §11 の Phase 4 完了条件「本番schemaエンドポイントが200を返し、Claude Code / Codex 双方から実測一致」
を確認するための手順書。対象は `estimate_dc_demand` / `validate_dc_params` / `simulate_dc`（Phase 7 段階4）。

姉妹プロジェクトでの前例と同じ方法で行う（`pv-sim-fip/docs/agent_design.md` §8.5）:
AIエージェントから自然言語で試算させ、ローカルの直接呼び出しの値と突き合わせる。

### 実施済み: MCPプロトコル層（2026-09-20、本番 `main` = 9bd6f97）

`https://hachinai-pv-sim-biz.hf.space/gradio_api/mcp/` へ汎用MCPクライアントと同じ手順で接続した（プロトコル 2025-03-26）。

- `tools/list`: 7ツール（`pv_sim_biz_` の接頭辞付き）。`simulate_dc` の入力は52項目
- `estimate_dc_demand` / `validate_dc_params` / `simulate_dc` を、**名前付き引数だけ**（エージェントの呼び方。
  未指定は既定値で補完）で呼び、ローカルの直接呼び出しと突き合わせ: 需要の見積り、受電上限1,190kW＋LP、
  上限を守れない診断の3ケースが**全項目一致**。不正入力は `error` / `errors` が返り、実行されない
- **検出した不具合（修正済み）**: `capacity_factor_pct` が numpy の型のまま返り、MCP経由だと数値でなく文字列
  （`"11.5"`）になっていた。産業用ツール・`estimate_pv_generation` にも以前からあった。`float` に変換して修正した（`f86f617`）。
  その後、公開ツール7つの成功系の `return` を `_jsonable()`（numpy型・辞書キーをJSON標準の型に揃える）で包む方式に一本化し、
  MCP出力がJSON標準の型だけであることをテスト（`test_mcp_dc_tools.py`）で確認するようにした
- MCPの応答本文はPythonの辞書表記（単一引用符）の文字列。Gradioの仕様で、産業用と同じ

## 事前準備

Codex CLI（登録済みなら再接続でツールが7つに増えているか確認する）:

## シナリオ

各シナリオのプロンプトをそのまま貼る。**「validate → 内容を提示して確認 → simulate」の2段階で動くか**も併せて見る
（本ツールの誤解釈ガードレール。`simulate_dc` はユーザーの確認後に呼ばせる）。

### S1. 需要の見積り（`estimate_dc_demand`、1秒未満）

> pv-sim-bizで、AI学習用のデータセンターの電力需要を見積もってください。IT容量2,000kW、IT負荷率90%、PUE1.3です。
> 年間の電力量とピークデマンド、受電電圧の目安を教えてください。

| 項目 | 期待値 |
|---|---|
| 年間IT電力量 | 15,768,000 kWh |
| 年間施設電力量 | 20,498,400 kWh |
| ピークデマンド | 2,501.8 kW |
| 負荷プロファイル | flat（定常） |
| 受電電圧の目安 | 特別高圧 30,000V（22・33kV） |
| 申請受電容量の目安 | 3,734 kW（ピーク÷0.67。「観測された上限で典型値ではない」との注記が付く） |

### S2. 受電上限を守れる（`validate_dc_params` → `simulate_dc`、約15秒）

> pv-sim-bizで、札幌のデータセンターにPVと蓄電池を入れる試算をしてください。IT容量1,000kW、IT負荷率80%、PUE1.4、
> 負荷形状はCEC実測形状でノイズなし（用途は手動設定）。PVは1,000kW（傾斜30度・真南）。蓄電池は2,000kWh、
> 充放電とも1,000kW、SOCは10〜90%で、最適充放電（LP）。系統受電の上限を1,190kWにしてください。
> 電気料金は基本料金1,890円/kW、電力量は夏季19.93円・その他18.77円、ほかは既定値です。

| 項目 | 期待値 |
|---|---|
| `validate_dc_params` | valid=true、警告1件（受電上限が厳しいとLPに時間がかかる旨） |
| 受電上限の状態 | `enforced`（LPで強制） |
| 導入前ピーク → 導入後ピーク | 1,207.4 kW → 1,115.3 kW（上限1,190kW内） |
| 年間発電量 | 1,007,698 kWh |
| 年間系統購入量 | 8,809,655 kWh |
| 蓄電池の年間充電量／放電量 | 63,104 kWh／56,952 kWh |
| 契約電力 | 1,207.4 kW → 1,115.3 kW |
| 年間コスト削減額（総合経済メリット） | 25,407,417 円 |
| 設備投資合計／単純回収年数 | 558,000,000 円／22.0 年 |
| CO2削減量 | 431.666 t-CO2/年 |

### S3. 受電上限を守れない（診断が返る、約2秒）

> 同じ条件（札幌・PV1,000kW・蓄電池2,000kWh/1,000kW・LP）で、IT容量を「中規模」の規模プリセット・用途をハウジングにして、
> 系統受電を「高圧6.6kVに収める（2,000kW未満）」にできるか試算してください。

| 項目 | 期待値 |
|---|---|
| 応答 | **エラーではなく診断結果**（`grid_cap_infeasible=true`、経済性の節なし） |
| 受電上限 | 1,999 kW（高圧に収める） |
| 導入前ピーク | 6,417.9 kW（IT 5,000kW × 80% × PUE 1.4 ×形状） |
| 違反 | 蓄電池の出力不足（power）と、エネルギー収支（energy） |
| 蓄電池が無限に大きくても必要な上限の下限 | 約 5,497 kW |
| 上限超過のコマ | 17,520件（年間の100%） |

エージェントが「上限を上げる／PVを増やす／IT負荷を下げる」といった次の一手を、`next_step` と説明文から正しく伝えられるかを見る。
**「蓄電池を大きくしても解決しません」というメッセージが落ちずに伝わるか**が要点。

### S4. 異常系

> pv-sim-bizで、用途が"warehouse"、PUEが0.5のデータセンターを試算してください。

期待: `error: パラメータ検証エラー`、`errors` が2件（用途の選択肢、PUEは1.0以上）。**計算は実行されず**、
エージェントが選択肢（`housing` / `ai_training` / `ai_inference` / `in_house_server_room` / `manual`）を
ユーザーに正しく示せるか。

## 判定

- **数値**: 上の期待値と一致（小数の丸め以外の差は不一致）
- **型**: `capacity_factor_pct` などが**数値**で返る（文字列にならない）
- **2段階プロトコル**: `simulate_dc` の前に `validate_dc_params` の内容をユーザーへ提示して確認を取る
- **警告の伝達**: S2 の警告（LPに時間がかかる）、S3 の「下限の目安」、S1 の申請受電容量の注記が、エージェントの回答に含まれる

## 結果の記録（実施したら追記）

### Codex CLI（2026-09-20）の所見

報告書は Codex 側（リポジトリ外）に保存。要点:

- **S1**: 年間IT電力量15,768,000 kWh／施設20,498,400 kWh／ピーク2,501.8 kW／特別高圧30,000V／申請受電容量3,734 kW／注記まで一致
- **S2**: `enforced`、導入前1,207.4 → 導入後1,115.3 kW（上限1,190kW内）、発電1,007,698 kWh、系統購入8,809,655 kWh、
  充電63,104／放電56,952 kWh、コスト削減25,407,417円、投資558,000,000円／回収22.0年、CO2 431.666 t。警告（LPの所要時間）も提示。
  補足: 上限を超えたのは12コマ（12 kWh）だけで、必要な蓄電池の下限は放電4 kW・使用可能7 kWh（2,000kWhは過大）
- **S3**: `grid_cap_infeasible=true`、違反はpowerとenergy、下限5,496.6 kW、17,520コマ全て超過。
  「蓄電池を大きくしても解決しません」を判断として伝え、`next_step`（上限を上げる／PV／IT負荷を下げる）も案内
- **S4**: 計算せず、選択肢とPUEの下限を提示
- **産業用（福岡・病院・LP・リース、余剰売電／逆潮流禁止）**: 2026-09-06の参照値と全項目一致
  （発電804,919 kWh、必要リース料23,750,289円、需要家メリット-2,175,000／-2,813,655円 ほか）

**気づき**
- 報告書の「サーバーバージョン 1.29.1 → 1.30.0」は、アプリの版ではなく **MCP SDKの版**（`serverInfo.version`）とみられる。
  再ビルドで依存パッケージが更新されただけで、計算には無関係
- 型（`capacity_factor_pct` が数値か文字列か）は報告書から読み取れない。プロトコル層の検証で数値を確認済み
- S4 では、エラーがあるのに「規模プリセットの区分は暫定値」の警告も出る（既定が規模プリセットのため）。害はないが冗長
- **Codexからの提案**: 特定日の日別・30分カーブをMCPから取得する専用ツールがない。Gradio UIの時系列を外部で使うには、
  日付指定の時系列取得ツール、または本計算結果に時系列を含める拡張が要る（→ 検討候補。CLAUDE.md「Phase 7 の残り」）
