## 判断の変遷

### 第1段階: 新規Spaceとして作る（2026-09-06）

`design_spec.md` §1-1 で決定。理由は3つ。

1. 気温連動PUE・IT負荷・受電容量上限といった**入力の主役がbizと異なる**ため、
   既に複数施設・モード切替・MGで複雑なbizのUIに足すと両方が使いにくくなる
2. 企画の狙いは「一連のMCP成果物を目立たせること」。MCP専用ツールは看板にならず、
   ブラウザで開いて触れる画面が要る
3. （暗黙の前提）**新規Spaceは無料で作成できる**

この判断のもとで Phase 0 を完了させた（commit `aea9165`）。

### 第2段階: PUEを一定値に簡略化（2026-09-14）

ユーザー判断「PUEはデフォルトで1.4、あとは手動設定でよいのではないか」。

- 出典不明の暫定パラメータ9個（α, COP_free, T_free, T_full, COP_ref, T_ref, β, COP_min, PUE_max）を
  UIから排除でき、「根拠の無い数値をデフォルトに埋めない」という本プロジェクト群の作法に最も忠実になる
- 失うもの: §9-1が差別化要素に挙げていた「DCは北に置くべきか」の定量化
  （北はPUEが低いが日射も少ない、というトレードオフ評価）
- **この決定により §1-1 の理由①が大きく弱まった**（後から見れば、ここが再検討の分岐点だった）

### 第3段階: HF仕様変更の判明（2026-09-14）

ユーザーが発見。**無料アカウントではGradio Spaceを新規作成できなくなっていた。**

> Static Spaces are free for everyone. Gradio and Docker Spaces run on compute and
> require a paid plan to create: PRO for personal accounts, Team or Enterprise for organizations.
> （https://huggingface.co/docs/hub/spaces-overview）

**§1-1 の理由③（暗黙の前提）が崩れた。** 詳細は設計書 §1-1・§13。

このとき案A〜Eを比較したが、**5案すべてが「別Space」を保ったままで、
bizへの統合案（＝§1-1の再検討）が構造的に欠けていた。** これは分析側の見落としである。

### 第4段階: biz への統合に方針転換（2026-09-14）

ユーザー提案「産業用＆MGプロジェクトで追加実装するほうが正しいか？」を受けて再検討。
§1-1 を支えていた3つの理由のうち**2つが既に崩れていた**ことが確認され、統合が最善と判断。

さらにユーザー提案「**タブで切り替える**」により、残っていた理由①も解消した。

### 第5段階: UI構成をタブ方式に決定（2026-09-14）

**需要設定セクションのみをタブで分割し、他は共通にする。**
全体をタブにするとPV面設定（8面×5項目＝40コンポーネント）等が二重定義になり app.py が肥大するため。

```
📍 地点選択                          ← 共通
⚡ 需要設定
   ┌[産業用・MG]─[データセンター]┐   ← ここだけタブ
   │ 施設プリセット   IT定格容量  │
   │ 複数施設合算     IT負荷率方式│
   │ モードA/B        PUE         │
   └─────────────────────────────┘
🔌 受電・売電（受電上限はDC時のみ表示） ← 共通
🔲 PV面設定（8面） / 🔋 蓄電池 / 💰 料金・経済性 / ▶️ 計算  ← 共通
```

出力側（月別・日別・デマンド・容量探索の4タブ）も共通。結果テキストのみDC時にPUE等を追加。
モードは `gr.Tab.select()` → `gr.State` で追跡し、`run_simulation` が `demand_source`
（"industrial" / "datacenter"）で需要生成器を切り替える。
**既存の計算パイプラインは (365,48) 配列を受け取るだけなので下流は一切変わらない。**

## 却下した案と理由

| 案 | 却下理由 |
|---|---|
| A. HF PRO課金（$9/月） | **コスト。** 円安下で年17,000円は重いとのユーザー判断（2026-09-14）。加えてPROが同時稼働8 units枠を広げるかは公式ドキュメントに記載がなく、5本目が動く保証がない |
| B. `pv-sim-gen` をリネームして転用 | `gen` を失う。リネームが作成制限を回避できるか未検証。**プロジェクト分離とコード重複1,255行はどちらも解決しない** |
| C. Static Space化（Gradio-lite） | **MCPサーバを公開できない**（静的ホスティングにサーバプロセスが無い）。技術的には可能なことを実測確認済み（設計書§13「案Cの実測検証」）だが、企画目的を失う |
| D. HF以外でホスト | ロリポップ！デプロイナウはPython非対応（Next.js/Nuxt/静的のみ）。マネージドクラウドは月1,348円でPROとほぼ同額 |
| E. 静的UI＋MCPを既存Spaceに相乗り | 実装が2箇所に分裂し、**Claude Code上も別プロジェクトになる**（セッション・メモリ・設定が分離）。scipy版とPuLP版で数値が食い違うリスクを単一実装で抑える必要があり保守が重い |

## この決定が解決しないこと（正直な記録）

**本決定は pv-sim-dc の公開先問題を解決するが、ロードマップの残り3本は解決しない。**

`next_development_idea.md` は本プロジェクトの後に「産業熱脱炭素」「DC冷却・排熱」「統合最適化」を
予定している。同じ理屈で3本ともbizに積むのは単一 app.py として無理があり、
**3本目・4本目の時点で同じ壁（新規Space作成の有料化・同時稼働8 units枠）に再び当たる。**
今回の判断は解決ではなく先送りである。目の前の1本に対しては最善だが、その認識を持って進めること。

### biz への追加実装スコープ

DCCNで削除した §4-2 の機能群は、bizでは**削除しない**。DCは選択肢の追加である。

## 作業上の注意

- **biz は公開中の本番Space。** リモートは2つあり、`origin` = HF Space（**push = 本番デプロイ**）、
  `github` = GitHub。作業はブランチを切って行い、push はユーザーの明示的な指示を待つこと
- Claude Code はチャット間で会話を引き継がない。引き継がれるのは
  **リポジトリ内のファイル**と**プロジェクトのメモリ**（`~/.claude/projects/<slug>/memory/`）のみ。
  判断の経緯は必ず本書か設計書に書くこと
- 実測で判明した重要事実（radiation.dbは50地点／需要が平坦だと蓄電池の価値がゼロ／
  PV単体では基本料金を下げられない）は設計書 §11 に記録済み
