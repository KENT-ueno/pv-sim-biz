## 判断の変遷

### 第1段階: 新規Spaceとして作る（2026-09-06）

`design_spec.md` §1-1 で決定。理由は3つ。

1. 気温連動PUE・IT負荷・受電容量上限といった**入力の主役がbizと異なる**ため、
   既に複数施設・モード切替・MGで複雑なbizのUIに足すと両方が使いにくくなる
2. 企画の狙いは「一連のMCP成果物を目立たせること」。MCP専用ツールは看板にならず、
   ブラウザで開いて触れる画面が要る
3. （暗黙の前提）**新規Spaceは無料で作成できる**

この判断のもとで Phase 0 を完了させた（commit `aea9165`）。

### 第2段階: PUEを一定値に簡略化（2026-09-14）

ユーザー判断「PUEはデフォルトで1.4、あとは手動設定でよいのではないか」。

- 出典不明の暫定パラメータ9個（α, COP_free, T_free, T_full, COP_ref, T_ref, β, COP_min, PUE_max）を
  UIから排除でき、「根拠の無い数値をデフォルトに埋めない」という本プロジェクト群の作法に最も忠実になる
- 失うもの: §9-1が差別化要素に挙げていた「DCは北に置くべきか」の定量化
  （北はPUEが低いが日射も少ない、というトレードオフ評価）
- **この決定により §1-1 の理由①が大きく弱まった**（後から見れば、ここが再検討の分岐点だった）

### 第5段階: UI構成をタブ方式に決定（2026-09-14）

**需要設定セクションのみをタブで分割し、他は共通にする。**
全体をタブにするとPV面設定（8面×5項目＝40コンポーネント）等が二重定義になり app.py が肥大するため。

```
📍 地点選択                          ← 共通
⚡ 需要設定
   ┌[産業用・MG]─[データセンター]┐   ← ここだけタブ
   │ 施設プリセット   IT定格容量  │
   │ 複数施設合算     IT負荷率方式│
   │ モードA/B        PUE         │
   └─────────────────────────────┘
🔌 受電・売電（受電上限はDC時のみ表示） ← 共通
🔲 PV面設定（8面） / 🔋 蓄電池 / 💰 料金・経済性 / ▶️ 計算  ← 共通
```

出力側（月別・日別・デマンド・容量探索の4タブ）も共通。結果テキストのみDC時にPUE等を追加。
モードは `gr.Tab.select()` → `gr.State` で追跡し、`run_simulation` が `demand_source`
（"industrial" / "datacenter"）で需要生成器を切り替える。
**既存の計算パイプラインは (365,48) 配列を受け取るだけなので下流は一切変わらない。**

### 第6段階: 段階2・3の実装（2026-09-19）

上記の方針どおり実装した。実装中に下した判断と、確認できた事実を記録する。

**判断**

- **`run_simulation` のシグネチャは末尾にキーワード引数（`demand_source`, `dc_args`）を足すだけ**にした。

  `dc_args` にまとめ、キーの並びは `DC_INPUT_KEYS`。UIの `on_click` が末尾の引数から `zip` で復元する

  DCCNにはなかった入力検証を追加（IT容量>0、IT負荷率は0超〜100以下、PUE≧1.0）。既定値は変えていない
- **PUEモードのUIは出さない**（一定値のみ）。第2段階の決定（PUEは一定・ユーザー入力）に従い、
  気温連動を選べるように見えるUIは置かない。`build_pue_30min` の気温連動は `NotImplementedError` のまま
- **北海道電力タリフ表はUIに接続していない**。CLAUDE.mdの指示「料金は共通のまま」に従い、DCも共通の
  「電気料金設定」（既定=東京電力EP）を使う。代わりにDC結果へ「ピーク2,000kW以上なら特別高圧が目安」という
  契約種別の食い違い警告を出す（既存の `contract_power_kw <= 2000` の境界と整合）。
  タリフ表の接続は下記のとおり不要と決定
- 蓄電池の充放電がゼロのときの注記と、`-0.0` の丸めは**DC時のみ**（産業用の出力は1文字も変えない）。
  注記文は「料金が年間単一単価」と断定しない（bizの共通料金は東京電力EPで夏季/他季の単価が異なるため）。
  日内の料金差（時間帯別単価）が無い点は両タリフに共通なので、その言い方にした

**確認できた事実**

- 産業用の既存挙動は不変: 5シナリオ（単一/複数施設・LP・ルールベース・リース/PPA・MG・両面・逆潮流禁止・需要なし）×

- 設計書 §5-7-6 の実測値を再現: 札幌・中規模5,000kW・PV5,000kW（方位角180°）で契約電力 6,417.9 → 6,285.3 kW
- **UIの「方位角」欄が未入力でも0を送り、既定の面1が北向きで計算される既存不具合を発見し、同日に修正した**
  （DC統合とは無関係。`gr.Number(value=None)` が0を送る仕様を最小アプリで確認 → `gr.Textbox`（空欄=未指定）に変更。
  詳細は CLAUDE.md「修正済み」）。設計書の実測値との0.8kWの差はこれで説明できた。
  **既定入力の発電量が約+48%になる挙動変更**（従来が過小）。本番（main）には2026-09-19に反映済み
- **北海道電力タリフ表のUI接続は不要**（ユーザー判断 2026-09-19）。料金は共通の「電気料金設定」に手入力で足りるため。

### 第7段階: 段階5（受電上限制約）の実装（2026-09-19）

段階の順序は「段階5（受電上限）→ 段階4（MCPツール）」とした。段階5で `optimize_battery()` に引数が増えるため、
先にMCPツールを作るとスキーマ（外部に公開されるインターフェース）を後から作り直すことになる。

**ユーザーからの入力**

- 日本の受電上限は電圧階層の境界が実質的な制約になる: 高圧6.6kV＝2,000kW未満、22・33kV＝10,000kW未満、
  それ以上は66kV。**154kVは考えなくてよい**。→ 上限の選択肢はこの境界そのものにする
- **需要を調整すること（IT負荷のシフト）も上限を守る手段として考慮すべき**（変数が多いので段階を分ける）

**判断**

- **上限は境界の1kW下**（1,999 / 9,999kW）にする。`resolve_voltage_class` は2,000kWちょうどを特別高圧に分類し、
  LPは上限に張り付くのが通常なので、境界値のままだと「高圧に収める」という意図から外れる。
  プリセットは `VOLTAGE_CLASS_THRESHOLDS` から導出し、定義の二重化を避けた
- **上限を守れないとき（実行不可能）は診断メッセージを返す**（ユーザー選択: 診断＋必要量の目安）。
  厳密な最小構成の探索はしない。必要条件3つ（energy/power/capacity）で判定し、必要量は下限の目安と明記する。
  必要条件が破れていればLPを解かず即座に返す（CBCの実行不可能判定を待たない）
- **蓄電池が「なし」「ルールベース」のときは上限を強制しない**（ユーザー選択: 超過判定のみ表示）。
  ユーザーが選んだ蓄電池モードを勝手に変えない。導入後ピークが上限を超えるかの判定と必要量の目安だけを出す
- **上限ありのLPだけ周期SOC**（初期SOC＝年末SOC）。年初に蓄電池が空から始まる人工的な実行不可能を避ける。
  上限なしのLPは従来のまま（産業用の出力を変えない）
- 受電上限の入力は**DCタブの中**に置いた（設計の当初図は共通セクション内の「DC時のみ表示」だった）。
  表示制御が不要になり、産業用タブで選んだ値が残って効いてしまう（隠れた入力値の残留）問題も構造的に避けられる。
  `resolve_dc_demand` が上限を解決するので、産業用モードには上限が存在しない
- **需要側の調整は段階5では入れない**（ユーザー選択: 段階5を先に完成）。当初は「段階6」として次に実装する予定だったが、
  直後に**保留へ変更した（下の第8段階）**

**確認できた事実**

- 診断は健全: 乱数の小問題60ケースで「診断が守れないと言う ⇔ LPが実行不可能」が完全に一致
  （充電電力を十分大きくすると3条件は必要十分。不可能42件/可能18件）
- 産業用の既存挙動は不変: 段階2・3と同じ5シナリオ×7項目の出力保存→照合で全て同一（`optimize_battery` の内部を触ったため確認）
- 数値の検算: 札幌・中規模5,000kW・PV5,000kWで、PV差引後の平均負荷は約5,025kW、蓄電池を無限に大きくしても
  必要な上限の下限は約5,059kW（効率損失分だけ平均より高い＝理屈どおり）。「高圧に収める（1,999kW）」は
  この規模では蓄電池では不可能で、診断がそう返す
- 上限が厳しいとCBCが遅い（充電レートを極端に絞ると1回約37秒。時間制限120秒）。実運用の範囲では6〜14秒
- `infeasible_lp`（診断の必要条件は満たすがLPが解けない＝主に充電レート不足）は、実シナリオでは再現しにくい
  （現実的な設定ではどれも解けた）。合成データで経路を確認した

### 第8段階: 需要シフト（段階6）を保留にし、範囲を第一弾＋DC固有機能に戻す（2026-09-19）

**経緯**: 段階5の相談で「需要を調整することも考慮せねばならない」と出て、「柔軟なIT負荷の割合[%]」を段階6として

**判断（ユーザー: 「需要シフトは保留にして開発を進める。ここをいじり始めるとよくない」）**

- **段階6（需要シフト）は保留**。設計書 §7 の位置づけ（DCCN Phase 5・将来・簡易版の範囲外）に戻す

- 上限を守る手段は蓄電池のみ。診断メッセージから「需要シフトを今後実装予定」の案内は外した

- 「DC需要を規模で変えて試す」は既に実装済み（規模プリセット4段階＋用途プリセット＋IT容量直接／ラック数×density。
  時間変動はCEC実測形状／日変動／ノイズ）。数値は暫定値と明記済み

### 第9段階: 段階4（DCのMCPツール）の実装（2026-09-19）

**判断**

- **既存の産業用計算経路を再利用する**。`_run_industrial_simulation` に `demand_override`（需要の差し込み）と
  `grid_cap_kw` を省略可能な引数として足し、DC用の別実装は作らない。産業用は引数を省略した呼び出しのままで、
  HEAD版との突き合わせで出力がビット同一（4シナリオ×simulate/validate。MG・PPA・両面・LP・逆潮流禁止を含む）
- **`estimate_pue` は作らない**。PUEは一定値で地点に依存せず、意味のある出力がない。気温連動PUEを再開するときに追加する
- **受電上限を守れないことは `error` にしない**。ユーザーにとっては「答え」（この条件では守れない、必要量の目安はこれ）であり、
  エージェントが次の提案（上限を上げる／蓄電池を増やす）をするための情報を持つため、`grid_cap_infeasible: true` の
  診断結果として返す。入力の不備だけが `error`
- **MGはDCツールで扱わない**（`mg_*` 引数なし）。UIのDCタブは共通のMG設定が効くが、MCPでは需要施設が1つの
  DCで、束ねメリットの前提（複数施設）が成り立たないため
- **DC入力は簡易キー**（`housing` / `hv_under_2000kw` など）にして、日本語ラベルとの対応は `_dc_maps()` に集約。
  対応が app.py の定義と食い違わないことをテストで確認する
- 契約種別（高圧/特別高圧）の既定は `high_voltage`（UIと同じ）。ピークが2,000kW以上なら警告で知らせる。
  自動で切り替えない（結果に効く既定値を黙って変えないため）

**確認できた事実**

- UI（`run_simulation`）とMCP（`simulate_dc`）で、年間系統購入量・導入後ピークが一致（LPも決定論的に同じ）
- `gr.api` 経由でHTTP（`/gradio_api/call/…`）でも動作。スキーマは7ツール
- 気づき: `simulate_*` ツールは引数の説明が空（産業用の既存の挙動と同じ）。`validate_*` に全引数の説明を置く運用

### 第10段階: 「受電増強 vs PV/蓄電池」の比較機能は作らない（2026-09-19）

**検討**: 設計書 §7-1 の比較（受電増強か、PV・蓄電池で上限内に収めるか）を段階として実装するか検討した。
既存の産業用にこの比較機能はなく、あるのは「高圧→特高で受電設備工事費27,500円/kVAを初期投資に足す」処理だけ。

**既存の単価で試算した結果**（東京電力EPの既定料金、DC・CEC形状・負荷率80%・PUE1.4。参考値）:
- 特高化は電気代が年22〜75M円安く、工事費（27,500円/kVA）を約2.4年で回収する。規模に依らずほぼ一定
- 蓄電池で1,999kWに収められるのは、ピークが境界をわずかに超える範囲（IT 1,600〜1,700kW程度）だけ。平坦な需要は
  平均が境界に近づくと蓄電池では守れない。収められる場合も蓄電池の費用は特高化の数倍になりうる（1,700kWで約2億円 vs 約60M円）

**ユーザーの指摘**:
- 27,500円/kVAは**高圧の受電設備の単価で、特高ではない可能性が高い**。特高の単価はもっと高いはずで、高圧→22kVでも
  特高が有利になりやすいという今の試算は前提が崩れている（出典の記録もない）
- 22・33kV→66kV（10,000kW境界）の単価は存在しない
- 蓄電池でできることは単価が高く、たかが知れている（試算と一致）
- 系統増強待ちや高圧・特高の違いは単価で表せず、現時点の単価での比較は意味をなさない

**判断（ユーザー: 「比較機能は不要かもしれない。とりあえずシミュレーションできます、くらいに収める」）**
- 比較機能は作らない。「参考比較の1行」を診断に足す案も、単価が信用できないため取り下げた
- 「シミュレーションできる」の範囲は、受電上限の診断（段階5: 守れるか／守れないなら必要な蓄電池の下限の目安）までとする
- 27,500円/kVAは値を変えず、出典が確認できていない旨を CLAUDE.md・設計書に記録した（手入力で変更可）。
  特高の単価が分かれば、産業用の「高圧→特高」の初期投資も改善できる
- 産業用（+MG）への展開は不要になった（比較自体を作らないため）

### 第11段階: MCP実機検証の準備と文書整理（2026-09-20）

**MCPプロトコル層の検証で見つけた不具合**: 汎用MCPクライアント（`initialize` → `tools/list` → `tools/call`）で本番に接続し、
ローカルの直接呼び出しと突き合わせたところ、`capacity_factor_pct` が `numpy.float64` のまま返り、MCP経由だと
**数値でなく文字列（`"11.5"`）** になっていた。ローカルの直接呼び出しとHTTPの `/call` では数値として比較が通るため、
これまでの検証（産業用のCodex検証を含む）では検出できなかった。産業用ツールと `estimate_pv_generation` にも以前からあった。
まず個別に `float()` へ変換して修正し（`f86f617`）、その後、公開ツール7つの成功系の `return` を `_jsonable()` で包む方式に一本化した
（機構を1つに絞ると差分が小さく、grepで確認でき、今後の変更でも再発しない。デコレータ方式はGradioがシグネチャ・docstringから
MCPスキーマを作るため避けた。公開7ツールのシグネチャ・docstringは変更前と同一）。テストは「JSON標準の型だけ」の検査に拡張した。**pv-sim-gh・pv-sim-fip も本番で同じ症状**
（`estimate_pv_generation`。gh は `payback_years` も）を確認し、**両リポジトリでも `_jsonable()` に統一して修正済み・本番確認済み**
（gh `3abba28`／fip `f2a50f9`。修正前後の出力は gh 23条件・fip 33条件で完全一致）。

**判断**
- 実エージェント（Codex / Claude Code）での検証は、こちらから実行できないため**手順書**（`docs/dc_agent_verification.md`）にした。
  プロンプト・期待値（ローカル計算値）・判定基準・結果記録欄を用意。プロトコル層の検証結果は同書に記録
- 文書整理: 設計書 §13 の古い項目（公開手段の案A〜E。統合で解決済み）は **付録A** に移して圧縮。§11 に
