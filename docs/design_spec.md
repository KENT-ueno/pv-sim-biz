## 1. プロジェクト概要

データセンター（DC）を大口需要家として扱い、**IT負荷・冷却（PUE）・PV・蓄電池・系統受電制約・
電気料金・CO2・事業性**を日本条件で一気通貫に評価する簡易シミュレーター。

**ペルソナ:**
- a) DC事業者/データセンター開発者（立地選定・受電容量・PV/BESS導入の初期検討）
- b) 需要家企業・SIer（自社DC/サーバー室の脱炭素化と電気代削減の効果試算）
- c) エネルギー系コンサル・投資家（AI DCの電力制約と採算性の概算）

## 5. DC需要モデル（本プロジェクトの核心）

### 5-1. 前提: ComStockにデータセンターは存在しない（2026-09-06 実査確認）

pv-sim-bizの需要プリセットはNREL ComStock（End-Use Load Profiles。NRELは2025年に
**National Laboratory of the Rockies / NLR** へ改称）の実データを
静的CSVで同梱している（AMY2018、ASHRAE気候区分4A、30分値、m²あたり原単位）。
しかしComStockの建物タイプは以下14種のみで、**DataCenterは存在しない**:

```
FullServiceRestaurant, Hospital, LargeHotel, LargeOffice, MediumOffice,
Outpatient, PrimarySchool, QuickServiceRestaurant, RetailStandalone,
RetailStripMall, SecondarySchool, SmallHotel, SmallOffice, Warehouse
```

これはComStockの母体であるCBECS調査にDCのサンプルがほぼ無いという、データセット側の
構造的欠落。最も近い `Warehouse` も低負荷・平坦・気象依存が薄く、DCの負荷形状とは似ていない。

**→ 実在建物統計の流用は断念し、物理モデルで合成する。**
これは妥協ではなく、むしろDCの負荷は「IT負荷＋冷却」という単純な構造のため
合成の方が実態に近く、かつ外気温連動PUEという当初からの狙いとも自然に整合する。

### 5-2. 需要の定義

各30分コマ *t* について:

```
demand(t) = IT_load(t) × PUE(T_out(t))            [kWh/30分]
```

- `IT_load(t)`: サーバー等IT機器の消費電力量 [kWh/30分]
- `PUE(T)`: 外気温 *T* におけるPower Usage Effectiveness（施設全体 / IT機器）
- `T_out(t)`: 外気温 [°C] ← `radiation.db` の要素5を `prepare_30min_data()` で30分補間したもの

### 5-3. IT負荷モデル

```
IT_load(t) = IT_capacity_kw × load_factor(t) × 0.5     [kWh/30分]
```

`load_factor(t)` は3方式から選択:

| 方式 | 内容 | 想定用途 |
|---|---|---|
| 定常 | 年間一定の負荷率 | AI学習用DC・ハイパースケール（デフォルト） |
| 日変動 | 昼夜で負荷率が変動（ピーク時刻・ピーク/ボトム比を指定） | エンタープライズ/推論系 |
| CSVアップロード | 17,520行の実測IT負荷 | 実データを持つユーザー |

**設計判断:** 日変動プロファイルは「ピーク時刻」「ピーク負荷率」「ボトム負荷率」の3点を
正弦波で補間する簡易方式とする。DCの負荷変動は建物用途と違い外気に依存しないため、
ComStock由来の複雑な曲線を持ち込む必要はない。

### 5-4. PUEモデル（気温連動）

施設電力の内訳から出発する:

```
P_total = P_IT + P_cool + P_other
P_other = α × P_IT              （UPS/変圧器損失・照明等。気温にほぼ非依存）
P_cool  = P_IT / COP_eff(T)     （IT機器の発熱をそのまま除去する前提）

⇒ PUE(T) = 1 + α + 1 / COP_eff(T)
```

`COP_eff(T)` は外気冷房（フリークーリング）と機械式冷凍機の遷移帯を線形ブレンドする:

```
x = clip( (T − T_free) / (T_full − T_free), 0, 1 )     … 機械式冷凍機の寄与率
COP_mech(T) = max( COP_min, COP_ref − β × (T − T_ref) )
1 / COP_eff(T) = (1 − x) / COP_free + x / COP_mech(T)
```

さらに `PUE_max` で上限クリップする（設備の能力上限を超えて劣化し続けないため）。

**デフォルト値（暫定・要検証）:**

| 記号 | パラメータ | デフォルト | 単位 | 備考 |
|---|---|---|---|---|
| α | 電源設備損失率 | 0.10 | — | UPS/PDU/変圧器/照明。IT負荷比 |
| COP_free | 外気冷房時COP | 25 | — | ファン動力のみ |
| T_free | 外気冷房上限温度 | 15 | °C | これ以下は外気冷房のみ |
| T_full | 機械式冷凍機フル稼働温度 | 20 | °C | これ以上は機械式のみ |
| COP_ref | 冷凍機COP（基準温度時） | 4.5 | — | 空冷チラー想定 |
| T_ref | COP基準外気温 | 25 | °C | |
| β | COP温度勾配 | 0.08 | /°C | 外気温1℃上昇あたりCOP低下 |
| COP_min | 冷凍機COP下限 | 2.0 | — | |
| PUE_max | PUE上限 | 1.80 | — | |

このデフォルトでの計算例:

| 外気温 | COP_eff | PUE |
|---|---|---|
| 5 °C | 25（外気冷房） | 1.14 |
| 15 °C | 25（外気冷房） | 1.14 |
| 20 °C | 4.9（機械式） | 1.30 |
| 30 °C | 4.1 | 1.34 |
| 35 °C | 3.7 | 1.37 |

> **⚠ 出典に関する注意（本プロジェクトの作法）:**
> 上記デフォルトは物理的に妥当なオーダーではあるが、**特定の公表資料に基づく数値ではない**。
> 実装時に日本データセンター協会（JDCC）・環境省/経産省のDC実態調査等でPUE実績値と
> 突合し、`docs/pue_model.md` に出典付きで記録すること。
> 姉妹プロジェクトの慣行（三菱総研資料はページ番号まで記録、根拠の無い値はデフォルト0にする等）に
> 従い、**検証前は「暫定値」であることをUI上にも明示する**。

**簡易モード:** PUE一定（気温非依存）も選択できるようにする。既存DCの実績PUEを
持っているユーザーはそれを直接入れられる方が早い。気温連動は「立地比較」のための機能。

> ⚠ 出典整理の元資料はChatGPT出力だったが、記載されたURL・DOI・数値をすべて一次資料で検証し、
> 一致を確認済み。以下の引用はすべてCEC原文（`Data_Center_Methodology_Memo_ada.pdf`, 24頁）から。

#### (1) 商用DCの負荷形状 — CEC 2025 IEPR

カリフォルニア州エネルギー委員会が、7電力会社のinterval meterデータおよび
**PG&Eの約100データセンター（2020-2024年）**をもとに代表負荷曲線を作成している。原文:

> The data show that data centers:
> • Operate at high and sustained load factors throughout the day
> • Have little variation between daytime and nighttime hours
> • Show modest seasonal differences between summer and winter months
> • Run consistently across most hours of the year
>
> Across the sampled facilities, **average hourly load factors ranged from approximately
> 85 to 90 percent of observed annual maximum demand.**

> In the model, **weekday load peaks around hour ending 15 (2-3 p.m.) and weekend demand
> peaks around hour ending 17 (4-5 p.m.)**, consistent with observations in the interval meter data.

**本設計への含意:**

| 本モデルの設定 | 実測との対照 | 判定 |
|---|---|---|
| IT負荷率方式「定常」を既定にした（§5-3） | 「昼夜差が小さく年間を通じて高負荷」という実測と整合 | ✅ **裏付けあり**。推測ではなくなった |
| 日変動のピーク時刻デフォルト **14時** | CEC: 平日 hour ending 15（14-15時） | ✅ **ほぼ一致** |
| 日変動のボトム負荷率デフォルト **50%** | CEC: 時間別負荷率は年間最大需要の85〜90%に収まる | ⚠ **商用DCとしては振れ幅が深すぎる**。エンタープライズDC想定なら許容だが、既定値の見直し余地あり（変更時はユーザー確認） |

#### (2) 受電容量と実需要の関係 — Phase 2（受電上限制約）に直結

CECは**申請受電容量 → 想定最大運転需要**の変換係数として67%を採用している。原文:

> A **67 percent utilization factor** is applied to requested capacity … The utilization factor
> translates requested service capacity into expected maximum operating demand based on
> observed operations and utility input. This value is based on input from Silicon Valley Power
> (SVP) … Among SVP's existing data centers, observed peak demand relative to requested
> service capacity has ranged below this level, with **67 percent representing the upper end of
> observed utilization.**

つまり概念的な連鎖は次のとおり:

```
申請受電容量（Requested Service Capacity）
  × 67%（utilization factor）        ← 系統側に申請する容量と実際の最大需要の差
  → 想定最大運転需要（Maximum Operating Demand）
  × 85〜90%（hourly load factor）    ← 最大需要と各時間の需要の差
  → 典型的な時間需要
```

**この67%は §7 の `grid_import_cap_kw` の設定指針に直接使える。**
逆算すると「必要な申請受電容量 ≒ 施設最大需要 ÷ 0.67」。
受電上限を絞ったときの診断メッセージ（§13の未確定事項）にもこの根拠を使える。

> **混同禁止**: 67%（申請容量→最大需要）と85〜90%（最大需要→各時間需要）は**分母が違う別物**。
> CEC原文も "The interval meter analysis was **not** used to derive the 67 percent utilization
> factor." と明記している。
> さらに**本モデルの「IT負荷率」はIT定格容量に対する比**であり、上記2つのいずれとも分母が異なる。
> 3つを同一視しないこと。

#### (3) PUEモデルの検証データ — NLR ESIF HPC

旧NREL（**2025年にNational Laboratory of the Rockies / NLR へ改称**）が、ESIF HPCデータセンターの
実測時系列を公開している。`it_power_kw` / `cooling_kw` / `hvac_kw` / `pump_kw` /
`plug_and_light_kw` / `pue` が**用途別に分離**され、別ファイルで外気温・相対湿度も提供される
（Parquet・圧縮CSV、DOI: 10.7799/3015212、実在を確認済み）。

**⚠ 当初「§5-4のPUEモデルを検証できる唯一の実測データ」と記載したが、これは誤りだった（2026-09-18訂正）。**
ESIFの施設仕様を調べたところ、本モデルの前提と根本的に異なることが判明した。

| 項目 | ESIF | 本モデルの前提 |
|---|---|---|
| PUE | **1.06**（世界最高水準の12ヶ月移動平均） | 既定 1.40 |
| 冷却方式 | **チラーレス**。温水直接液冷（最高75°F≒24℃）＋蒸発冷却塔 | **空冷・機械式チラー**（§5-5で液冷はスコープ外と明記） |
| 排熱 | **97%回収**、ERE≒0.7。建物暖房・歩道融雪に利用 | 排熱利用はスコープ外 |
| 立地 | ゴールデン（標高約1,700m・乾燥） | 日本（多湿） |

**致命的なのは冷却方式である。** §5-4のモデルは `COP_mech(T) = max(COP_min, COP_ref − β(T − T_ref))`
という**機械式チラーのCOP温度依存**を骨格にしているが、**ESIFにはチラーが存在しない**ため
関数形そのものが適用できない。加えて蒸発冷却は乾燥したコロラドで極めてよく効くが多湿な日本では
性能が落ちるため、気温応答も転用できない。

**→ PUEデフォルト値の較正には使えない。§13の宿題（JDCC・環境省/経産省のDC実態調査との突合）は
未解決のまま残る。**

**「偏りの確認」と「モデルの適用不可」は別problemである（公平のための注記）。**
元の調査資料（`docs/dc_load_data_sources.md` §10）は、ESIFを単独の情報源として使うのではなく
**CEC約100施設の集約曲線と突き合わせて偏りを確認する**3点測量として提示しており、
HPC施設であることの留保も自ら明記している。この方法論自体は妥当である。用途別に整理すると:

| 用途 | 評価 |
|---|---|
| **負荷形状の偏り確認**（ESIF vs CEC） | ✅ 方法論として妥当。ただし本プロジェクトにとっての価値は限定的で、
得られる結論は「HPCは商用DCと異なる」という既知の事実に留まる。商用DCの参照としてはCECを直接採ればよい |
| **PUE較正** | ❌ **偏りの問題ではなく母集団が違う。** 偏り確認とは同じ母集団の偏ったサンプルを基準と
突き合わせる作業だが、ESIFにはチラーが無いため**比較すべき関数形そのものが存在しない**。
「ESIFのβは商用DCより何%ずれている」という補正のしようがない。
なおCECもPUEは持たない（interval meterは施設全体の受電量のみ）ため、
**PUEを較正する基準が3点測量の中に存在しない** |

**ESIFだけが持つ価値**: CECは施設全体の受電量しか持たないが、ESIFは**ITと冷却を分離**している。
`demand = IT × PUE` という本モデルの**分解構造そのもの**を実データで見られるのはESIFだけである。
ただしESIFは年間を通じて実質フリークーリングのため冷却電力の外気温応答が平坦で、
**機械式チラーが立ち上がる遷移帯（§5-4モデルの肝）が観測されない**。構造検証としても見たい部分が写っていない。

需要プロファイルの「情報源」としては不適。n=1の研究施設であり、HPCのジョブスケジューリング
（バッチ投入・メンテナンス窓）に支配された負荷形状は商用DCを代表しない。

**ただし `next_development_idea.md` 項目3（データセンター熱モデルへの展開：液冷・CDU・
排熱利用・TES）では第一級の参照データになる。** 温水直接液冷の実測、排熱97%回収・ERE 0.7の実績、
IT/冷却/HVAC/ポンプの用途別分離、外気温・相対湿度の同時取得——項目3が必要とするものが揃っている。

出典: https://www.nrel.gov/computational-science/warm-water-liquid-cooling ／
Better Buildings Solution Center "NREL's Energy Systems Integration Facility"

#### (3-b) 時間粒度に関する原則（データソース共通）

調査資料は「1時間平均にリサンプリングして8760時間データとして利用」と書いているが、
**本プロジェクトの用途では粒度が粗すぎる。**

本モデルは30分ベース（17,520コマ）であり、**契約電力は「30分デマンドの年間最大」で決まる**
（`calc_electricity_cost()` は `demand × 2.0` でkW換算し年間最大を取る）。
1時間平均を取るとピークが平滑化され、**契約電力＝基本料金を過小評価する**。

**外部データを取り込む場合は8,760点ではなく17,520点（30分平均）で取ること。**
1時間値しか無いデータを48コマへ内挿すると、存在しない滑らかさを捏造することになる
（`interpolate_to_30min()` はNEDO気象データの毎時値を扱うための関数であり、
需要データに同じ扱いをしてよいわけではない）。

#### (4) 任意条件の負荷曲線生成 — LBNL Data Center Load Shape Maker

LBNLが公開するPython製ツール（実在を確認）。15分×365日＝**35,040点**の年間負荷曲線を生成でき、
分類軸は規模（大中小）／用途（**Training・Inference・Mixed**）／冷却（空冷・水冷）／
日内形状（Flat・Business diurnal・Business high diurnal・Customer diurnal・Customer high diurnal）／
ノイズ（低3-7%・高12-18%）。

本モデルの「定常／日変動」2択より分類が細かく、**将来の拡張指針として有用**。

#### この発見が変えないこと

**§5-1 の結論は覆らない。** ComStockにDataCenterが存在しないことに変わりはなく、
上記はいずれも**日本条件の需要プロファイルを直接与えるものではない**（すべて米国データ）。
IT負荷の「形」はワークロード起因なので転用可能性が高いが、PUEの水準は気候・設備に依存するため
米国値をそのまま使うのは危険（本モデルはPUEをユーザー入力にしたのでこの点は問題にならない）。

**変わるのは「合成モデルのデフォルト値に出典を与えられる」こと。**
本プロジェクト群の作法「根拠の無い数値をデフォルトに埋めない」に直接効く。

### 5-7. 需要モデルの実装（2026-09-19。水準と形状の分離）

§5-6の調査結果を受けて需要モデルを再構成した。**核心は「水準」と「形状」を分けること**である。

```
IT_load(t) = IT定格容量 × IT負荷率（年平均） × 形状(t) × 0.5   [kWh/30分]
                            └ 水準:サイト固有    └ 形状:出典あり（年平均=1.0に正規化）
```

こうすると「引用できる部分（形状）」と「ユーザーが決める部分（水準）」が混ざらない。
全プロファイルで形状の年平均が1.0なので、**プロファイルを切り替えても年間電力量は変わらない**
（スモークテストで検証済み）。

#### 5-7-1. 容量の指定（3方式）

内部では常に IT容量[kW] に正規化する（`resolve_it_capacity_kw()`）。

| 方式 | 内容 |
|---|---|
| 規模プリセット | エッジ 300 / 小規模 1,000 / 中規模 5,000 / ハイパースケール 40,000 kW |
| IT容量を直接入力 | 「20MWのDC」という業界標準の言い方 |
| ラック数×density | ラック数 × ラック電力密度[kW/ラック]。設備設計者向け |

> **⚠ 規模区分は暫定値。** LBNL Shape Maker は large/medium/small を用いるが、
> **そのMW区分はリポジトリに公開されていない**（2026-09-19確認）。
> 上記はユーザー合意のうえ採用した業界一般の区分であり、出典のある数値ではない。
> 目安: エッジ 0.1〜0.5 ／ 小規模 0.5〜2 ／ 中規模 2〜20 ／ ハイパースケール 20〜100+ MW
>
> **延床面積[m²]は採らない。** DCはラック密度で電力密度が1桁変わるため、
> pv-sim-bizのComStock方式（m²あたり原単位）はDCに転用できない（§5-1）。

#### 5-7-2. 負荷プロファイル（形状）

| プロファイル | 形状の出典 |
|---|---|
| **CEC実測形状（米国商用DC）** | CEC 2025 IEPR 調和モデル。**平日/休日 × 12ヶ月 × 24時刻 = 576点**のテーブルを定数として内蔵（`CEC_LF_WEEKDAY` / `CEC_LF_WEEKEND`、千分率） |
| **定常（AI学習・ハイパースケール）** | LBNL Shape Maker: "Flat — no meaningful time-of-day variation, characteristic of large AI training clusters running continuous batch jobs"／PNNL-38601: "Active states … maintain elevated levels for tens of minutes to hours" |
| **日変動（自社サーバー室・業務連動）** | **出典なし**。振れ幅の大きいサイトを手で作る用途に限定。商用DCには使わない |

**CEC 576点テーブルの作り方（再現手順）**: `ALT_DATA_CENTER_GROWTH_HOURLY_MW_ada.xlsx`
（39MB、https://www.energy.ca.gov/media/12647 ）の `Planning_Scenario` シートから
`CAISO_supp`（調和モデル出力）の1年分を取り出し、年間最大で正規化して
(平日/休日 × 月 × 時刻) の平均を取る。**年による形状の差は最大0.054ポイントで実質不変**
（2030/2035/2040/2045で検証）。復元した形状はメモの記述と完全に一致した:

| 検証項目 | メモの記述 | 復元値 |
|---|---|---|
| 平日ピーク | hour ending 15 | ✅ hour ending 15 |
| 休日ピーク | hour ending 17 | ✅ hour ending 17 |
| 季節ピーク | 晩夏〜初秋 | ✅ 9月 96.2% / 8月 96.1% |

**実測が示した重要な事実**: 平日の日内変動は **91.0%〜95.7%（振れ幅わずか4.7ポイント）**。
本モデルの日変動デフォルト（ピーク90%／ボトム50% ＝ 40ポイント）は
**商用DCとして桁違いに深すぎる**。この値は「自社サーバー室」用途として残し、
**商用DCはCEC形状を既定とする**ことで棲み分ける。

**平日/休日の判定**: NEDO METPV-20は代表年データで曜日を持たないため、
`CEC_REFERENCE_YEAR = 2025` で暦を固定する。CECの平日/休日差は1〜3ポイントと小さいため影響は限定的。

#### 5-7-3. 短周期変動（ノイズ）

LBNL Shape Maker の定義に準拠: **低 3〜7% / 高 12〜18%**（baseline比）。
日ごとにノイズ強度を帯の中で変え、各コマに一様乱数を乗せる。
**再現性のため `NOISE_SEED` で固定**（同じ入力なら常に同じ結果）。

#### 5-7-4. 用途プリセット

| 用途 | プロファイル | ノイズ |
|---|---|---|
| ハウジング（コロケーション） | CEC実測形状 | 低 |
| AI（学習中心） | 定常 | 低 |
| AI（推論中心） | CEC実測形状 | 高 |
| 自社サーバー室 | 日変動 | 高 |

#### 5-7-5. 受電容量の目安表示

結果テキストに `施設最大需要 ÷ 0.67` を「推奨する申請受電容量の目安」として表示する。
**⚠ CECの67%は「観測された上限」であり典型値ではない**（§5-6(2)）。
CECは需要を多めに見積もるため上限を採用しているが、**逆算に使うと必要容量を小さく見積もる方向に働く**
（保守性の向きが反転する）。この注意書きをUIにも出している。

#### 5-7-6. 実装後の挙動変化

CEC形状は日中（hour ending 15）にピークを持つため、**PVが契約電力を削減できるようになった**。
Phase 0時点の「定常＋PUE一定」では需要が完全に平坦で、PVは電力量料金しか削れなかった（§11の事実3）。
実測（札幌・中規模5,000kW・PV 5,000kW）: 契約電力 6,417.9 → 6,285.3 kW（132.5 kW削減）。
**これは実データの形状を入れたことで初めて現れた、より現実に近い挙動である。**

## 7. LP定式化（bizからの差分）

目的関数・変数はbizの `optimize_battery()` をそのまま使う:

```
minimize  基本料金(peak_demand × 単価 × 12 × 力率係数) + 電力量料金 − 売電収入
```

決定変数: `charge(t)`, `discharge(t)`, `grid_import(t)`, `grid_export(t)`,
`curtailment(t)`, `soc(t)`, `peak_demand`（スカラー）

**追加する制約は1本のみ:**

```
grid_import(t) / 0.5 ≤ grid_import_cap_kw      ∀t     （受電上限が指定された場合のみ）
```

**この1本が本ツールの目玉になる。** 受電容量が足りない（系統増強が間に合わない）DCにおいて、
PV＋蓄電池が「受電上限を超えてIT負荷を賄う手段」として機能することを定量化できる。
制約が有効なとき、LPが実行不可能になる場合は「その受電上限ではこのIT負荷を賄えない」という
意味なので、**エラーではなく診断メッセージとして返す**（必要な追加PV/BESSの目安を添える）。

#### 実装メモ（2026-09-19、Phase 7 段階5）

- **実装**: `optimize_battery(..., grid_import_cap_kw=None)`。系統購入変数 `grid_import[t]` の上限を `cap × 0.5h` にする
  （`peak_demand ≥ 購入/0.5` があるので契約電力も上限以下になる）。上限なし（None/0）の経路は従来のLPとビット同一。
  上限を守れないときは `GridCapInfeasibleError`（`RuntimeError`のサブクラス）を送出する
- **境界の扱い**: 上限は境界そのものでなく**1kW下**（1,999 / 9,999kW）。LPは上限に張り付くのが通常で、
  `resolve_voltage_class()` は2,000kWちょうどを特別高圧に分類するため、境界値のままだと「高圧に収める」から外れる。
  プリセットは `VOLTAGE_CLASS_THRESHOLDS` から導出（定義の二重化を避ける）
- **周期SOC**: 上限ありのときだけ「初期SOC＝年末SOC（変数）」にする。従来の「初期SOC＝SOC下限（固定）」だと、
  年初1/1 0:00に蓄電池が空から始まる人工的な実行不可能が起きうる。上限なしの産業用LPは変えない
- **診断 `diagnose_grid_cap()`**（LPを解かずに必要条件で判定。§13の未確定事項を解消）。PV差引後の負荷 net = 需要 − PV が
  上限を超える分 `need⁺` は放電で、下回る余力 `need⁻` は充電の機会になる、という構造から3条件を判定する:
  1. **energy**: 年間で `Σneed⁺ ≤ η²·Σneed⁻`（破れると蓄電池を無限に大きくしても解決しない＝基底負荷が上限に近すぎる。
     二分法で「蓄電池が無限大でも必要な上限の下限」を出す）
  2. **power**: `max(need⁺)/0.5h ≤ 最大放電電力`
  3. **capacity**: 理想SOC（充電レート無制限）の最大ドローダウン（年をまたぐため2周分）≤ 使用可能容量
  3つとも**必要条件**なので、1つでも破れれば確実に守れない（LPを解かず即座に診断を返す）。必要量は充放電レート・効率損失を
  細かく見ない**下限の目安**で、実際にはこれ以上必要になりうる。3条件を満たすのにLPが実行不可能な場合は主に充電レート不足
- **診断の健全性検証**: 乱数の小問題60ケースで「診断が守れないと言う ⇔ LPが実行不可能」が完全に一致
  （充電電力を十分大きくすると3条件は必要十分になる。不可能42件/可能18件）。`test_grid_cap.py`
- **蓄電池が「なし」「ルールベース」（および最適容量探索）のとき**は上限を強制しない（ユーザーの蓄電池モードは変えない）。
  計算後の導入後ピークが上限を超えるかの判定と、必要な蓄電池の下限の目安だけを表示する。最適容量探索は上限を考慮しない
- **需要側の調整（IT負荷のシフト）は保留**（2026-09-19）。上限を守る手段は蓄電池だけ。診断メッセージは
  シフトを案内しない（実装しない機能を案内しないため）。経緯は decision_log 第8段階

### 7-1. 受電増強 vs PV/BESS の比較（本ツール独自の問い）

bizには既に**受電設備工事費 `SUBSTATION_COST_PER_KVA = 27,500 円/kVA`** が実装されている
（高圧→特別高圧変更時に計上）。これをDC文脈に読み替えると、次の二択を同じ土俵で比較できる:

| 選択肢 | コスト | 制約 |
|---|---|---|
| A. 受電容量を増やす | 27,500円/kVA × 増強量 ＋ 基本料金の増加（円/kW・月×12） | 系統側の空き容量・工事期間に依存 |
| B. PV＋蓄電池を入れる | PV単価×kW ＋ 蓄電池単価×kWh | 天候依存。夜間はBESS容量に律速 |

**「AI DCが系統に繋げない」という時事的な問題に対し、
"増強費を払う" と "自前で賄う" のどちらが安いかを日本の気象・料金条件で答えられる。**
これは既存3プロジェクトにも他の公開ツールにも無い切り口であり、
本企画の「目立たせる」という目的に最も直結する出力になる。

実装上は、選択肢Aのコストも評価期間のキャッシュフローに載せ、
**同一のNPV/IRRの土俵でA/Bを並べる**こと（片方だけ投資として扱うと比較にならない）。

### 需要側柔軟性（Phase 5・将来）

DCをフレキシブル需要として扱う拡張。バッチ的なAI学習ワークロードは時間シフト可能:

```
IT_load(t) = IT_base(t) + IT_flex(t)
Σ_day IT_flex(t) = 日次固定量        （1日内で移動可能、総量保存）
0 ≤ IT_flex(t) ≤ flex_max_kw × 0.5
```

これによりDCが「蓄電池を持たずにデマンドレスポンスできる需要家」になる。
簡易版のスコープ外だが、**設計上ここに入る**ことを明記しておく（LP変数の追加のみで実現可能）。

### 9-1. 分析上の見どころ（本ツールの訴求点）

実装後に必ず確認・記事化すべき論点:

1. **地点別の年間平均PUE**: 50地点の気温データから、北海道〜沖縄でPUEがどれだけ違うかを

3. **猛暑日の二重苦**: 外気温が高い日は冷却需要がピークになる一方、PVは温度上昇で出力が落ちる

   契約電力（基本料金）をどれだけ押し上げるか、蓄電池でどこまで削れるかを示せる。
4. **受電上限がボトルネックになるケース**: 受電上限を絞ったときに、PV＋BESSでIT容量を
   どこまで伸ばせるか。AI DCの系統制約という時事性の高いテーマに直接答えられる。

### Phase 0 実装で判明した事実（2026-09-06）

1. **`radiation.db` は 50地点。設計書初版の「77地点」は誤りだった。**
   fip / gh / biz 3プロジェクトの `radiation.db` は md5一致で同一ファイル（20,115,456 bytes、
   `5c71c471eff27745cb5eb042ca981f8e`）であり、`points` テーブルは50行。本設計書は全箇所を
   50地点に修正済み。**北海道はSAPPORO（14163）の1地点のみ**であり、北海道電力パイロット版で
   使える地点はこれ1点に限られる。§9-1の「地点別PUE比較」は50地点での比較になる。

2. **需要が平坦かつ料金が年間単一単価だと、蓄電池の価値は構造的にゼロになる（バグではない）。**
   IT負荷「定常」＋PUE一定では需要が24時間フラットになり、契約電力が全17,520コマで同値になる。
   ピークカットには全コマでの放電が必要で物理的に不可能。かつ北海道電力の一般料金は
   年間単一単価（§6-4）のため時間裁定も成立しない。LPは正しく charge = discharge = 0 を返す。
   実測（札幌、IT 1,000kW・負荷率80%・PUE1.40、蓄電池2,000kWh・LP）:

   | 条件 | 充電量 | 契約電力 | 電気代削減 |
   |---|---:|---:|---:|
   | 定常＋PV 1,000kW | 0 kWh/年 | 1,120.0 kW（削減0） | 2,600万円/年（PVのみの効果） |
   | 日変動＋PV 1,000kW | 226,037 kWh/年 | 1,259.4 → 1,019.9 kW（239.5kW削減） | 3,371万円/年 |
   | 定常＋PV 5,000kW（余剰発生） | 424,953 kWh/年 | 1,120.0 kW（削減0） | 9,073万円/年 |

   → 蓄電池の価値を出すには「需要に形を与える（日変動）」「余剰PVを作る」
   「時間帯別メニュー」「**受電上限制約（Phase 2）**」「JEPX連動（Phase 5）」のいずれかが必要。
   **Phase 2の受電上限制約が本ツールの目玉である理由がここで定量的に裏付けられた。**
   UIの結果テキストには充放電ゼロ時にこの理由を明示するようにしてある。

3. **PV単体では基本料金（契約電力）を下げられない。**
   平坦なDC需要のピークは夜間にも立つため、PVが削れるのは電力量料金だけ。
   契約電力の削減には蓄電池または需要側柔軟性（§7 Phase 5）が必要。
   これはDC特有の性質であり、需要が昼にピークを持つ一般の産業施設（pv-sim-bizの想定）とは
   PVの効き方が構造的に異なる。

      | **E. 静的UI ＋ MCPは既存Spaceに相乗り（ハイブリッド）** | 無料 | **案Cの唯一の弱点（MCP不可）を解消する**。UIは静的Space、MCPツールは既存の `pv-sim-biz` に `gr.api()` で追加。新規Space作成を一切伴わない。静的Spaceは8 units枠も消費せず、スリープもしない | 実装が2箇所に分かれる。MCPエンドポイントが `pv-sim-biz` になる意味的なねじれ。稼働中の公開Spaceを触るリスク |

      現時点の推奨は **A**（投じた工数に対し月$9は小さく、当初目的に最も忠実）。
      Bは無料で済むが未検証の回避策であり、`ge` を捨てる判断が別途要る。

#### 案E（ハイブリッド）の詳細（2026-09-14 追加）

**案Cを選ぶなら、案Eは案Cの上位互換である。** 静的化に必要な作業をすべて済ませた後、
MCPを足す追加コストが小さいため。

- 既存 `pv-sim-biz` は `mcp_tools.py` ＋ `app.py` の `gr.api(...)` 4行という確立した形を持つ。
  DC用ツール（`estimate_dc_demand` / `validate_dc_params` / `simulate_dc`）の追加は
  `dc_tools.py` を置いて `gr.api()` を数行足すだけ。`radiation.db` も既にある
- **新規Space作成を伴わないため、HFの作成制限に一切抵触しない。**
  自分のSpaceに機能を追加するのは規約上まったく正当であり、後ろ暗い回避策ではない

**成立の絶対条件: DC計算を scipy ベースで「1本だけ」書くこと。**
静的UI側（ブラウザ）とMCP側（biz上のサーバー）で別実装にすると、
**同じモデルの数値が食い違う**。シミュレータとしてこれは致命的。
幸い scipy/HiGHS はブラウザでもサーバーでも動くため（§13「案Cの実測検証」）、
**単一実装・2箇所ホスト**が成立する。PuLPは使わない。

**このルートを後押しする論点: ロードマップとの相性**
`next_development_idea.md` は本プロジェクトの後に「産業熱脱炭素」「DC冷却・排熱」
「統合最適化」の3本を予定している。**Freeの同時稼働枠は CPU runtime 8 units
（＝CPU Basic 4本）で既に埋まっており、PROがこの枠を広げるかは未確認**（§1-1）。
仮にPROでも枠が8 unitsのままなら、PRO課金しても5本目以降は同時稼働できない。
**静的Spaceはこの枠を消費しないため、案C/Eは本数がいくら増えても破綻しない。**
将来4本を並べる構想があるなら、案Eの方が長期的にスケールする。

**難点（正直な記録）**
- MCPツールが `pv-sim-biz` のエンドポイントから生えるため、命名が意味的にねじれる。
  ドキュメントで補える程度だが、きれいではない
- bizのツールスキーマが肥大する（現在4ツール → 7〜8ツール）
- 稼働中の公開Spaceを改修するリスク（テストで担保する）
- アーキテクチャが恒久的に分裂する（UI＝ブラウザ実行 / MCP＝サーバー実行）

#### 案Cの実測検証（2026-09-14、Pyodide 314.0.7 で実機確認）

当初「CBCがPyodideで動かないため実質不可」と記録したが、**これは誤りだった**。
CBCは確かに動かないが、**scipyがHiGHSソルバを内包しており代替できる**。
ブラウザ（Pyodide公式コンソール）で実測した結果:

| 項目 | 結果 |
|---|---|
| numpy 2.4.6 / pandas 3.0.2 / scipy 1.18.0 | ✅ `loadPackage` 6.3秒 |
| `scipy.optimize.linprog(method="highs")` | ✅ 利用可 |
| **蓄電池LP 実寸（T=17,520、変数105,121、制約87,600）** | ✅ **3.6秒で最適解**（ネイティブCBCの6.2秒より速い） |
| 同 T=1,440 | ✅ 0.4秒 |
| pvlib 0.15.2（micropip） | ✅ インストール7.3秒 |
| `get_solarposition()` 17,520コマ | ✅ 0.4秒 |
| `disc()` + `get_total_irradiance()` | ✅ 0.1秒 |
| solarfactors / pvfactors（両面パネル） | ✅ import成功（実計算は未検証） |
| sqlite3 | ✅ 3.39.0 内蔵 |
| tzdata | ⚠ `loadPackage("tzdata")` が別途必要（Asia/Tokyo解決に必須） |
| 初回ダウンロード総量 | ⚠ **約38.7MB**（scipy 13.2MB / pandas 4.0MB / numpy 2.8MB / wasm 3.3MB 等）。2回目以降はキャッシュ |

**20MBの `radiation.db` は障害にならない**: 1地点あたり必要なのは要素1(GHI)・5(気温)・積雪の
3要素×365日×24時間のみ。地点別に事前分割すれば1ファイル約50KB（圧縮後）で済む。

**したがって案Cを退ける理由は「技術的に不可能だから」ではなく、次の2点である:**
1. **MCPサーバを公開できない。** 静的ホスティングにはサーバプロセスが無く `mcp_server=True` が
   成立しない。§1-1が掲げる「一連のMCP成果物を目立たせる」という企画目的が達成できない
2. **LP定式化をPuLP→scipy疎行列に書き換える必要がある。** `optimize_battery()` 等の
   最も繊細な部分を姉妹3本と別実装にすることになり、「移植した関数は原則変更しない」という
   本プロジェクトの原則（§4-1）から外れ、4本の保守コストが上がる

**逆に言えば、MCPを諦めてよいなら案Cは現実的な選択肢である。**（未検証: Gradio-lite自体が
本アプリのUI（Plotly図・File入力・多数のイベントバインド）を問題なく動かせるか）

#### 静的Spaceの搭載数と容量（2026-09-14 調査・実測）

**個数の上限は公式ドキュメントに記載がない。** Spaces／リポジトリの「数」に対する制限は
storage-limits・spaces-overview のいずれにも無く、実質的な制約は次の2つだけ:

1. **ストレージ**: Freeアカウントのパブリックstorageは **"Best-effort"**。原文:
   > Beyond the first few gigabytes, please use this resource responsibly by uploading
   > content that offers genuine value to other users.

   つまり目安は「数GB」。加えて濫用防止の記述あり
   （"We do have mitigations in place to prevent abuse of free public storage"）
2. **静的Spaceは CPU runtime 8 units 枠を消費しない**（computeを使わないため）。
   Gradio/Docker Spaceの「同時4本」制約とは無関係

**本アプリを静的化した場合の容量（実測）:**

| 内訳 | 容量 |
|---|---|
| 気象データ 1地点分（要素1 GHI＋要素5 気温、int16＋gzip） | **16.6 KB** |
| 同 全50地点 | **0.81 MB** |
| 積雪（要素9、両面パネル用）を足しても | 約 1.2 MB |
| アプリコード（app.py相当＋HTML） | 約 0.15 MB |
| **自前ストレージ合計** | **2 MB未満** |
| Pyodide・gradio-lite・numpy/scipy/pvlib（38.7MB） | **0 MB**（CDN配信。自前storageを消費しない） |

現行の `radiation.db`（20MB）は全要素・全地点を持つが、静的版は必要要素のみを地点別に
分割配信すればよいため**25分の1以下**になる。
**目安「数GB」に対して1本2MBなので、個数は実質的に制約にならない**
（姉妹5本すべてを静的化しても合計10MB程度）。

**副次的な利点**: 静的Spaceはスリープしない。現行のCPU Basic Space（fip/gh/biz）は
48時間未使用でスリープし初回アクセスが遅くなるが、静的版は常時即応になる。
